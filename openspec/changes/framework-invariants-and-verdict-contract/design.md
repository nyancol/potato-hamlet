# Design

## Context

See proposal.md (Why) for motivation; see `specs/` for the normative requirements. This change absorbs the relationship vocabulary and process hierarchy
previously planned as `process-lifecycle-vocabulary`: those two were split on which files each
touched, but a snapshot's `ballots` and `box` fields are lists of pairs, and expressing a pair as a
graph individual needs two relations per entity, so the graph work cannot be completed without the
relation vocabulary. Three facts from the shipped artefacts shape the approach.

First, `law-extraction`'s review gate is structurally incapable of catching a non-conforming law. `scripts/check.py:check_ontology()` asserts exactly two things — every `ph:` class has a GFO superclass, and every `ph:` individual has `rdfs:label`. A law that declares no individuals therefore satisfies the individual check vacuously. This is how `artefacts/mayor-2027` came to carry `ph:MayorElectionCycle` with no date properties and no cycle individuals, while `artefacts/mayor-quorum` carries the full calendar contract: both pass `check.py` and both are frozen. Any new invariant that is only checked per-*instance* will fail the same way, so this change's invariants are deliberately declared as checks on **classes and property declarations**, which exist regardless of instance population.

Second, the intended scope is far wider than elections — purchase requisitions, taxation, and other processes with genuinely divergent state schemas. So the design target is not "unify the schemas" but "make a consumer able to bind to whatever schema a law declares". That reframing is what removes the flat-versus-history question from the consumer's problem entirely.

## Goals / Non-Goals
**Goals:**
- A law-agnostic consumer binds to a law through its declarations, never through knowledge of that law.
- Framework invariants are checkable on the TBox alone, so they cannot pass by absence.
- The verdict contract has no field named for a specific process, so a new process needs no contract change.
- The consumer performs no calendar arithmetic and derives no authority rule.

**Non-Goals:**
- Unifying laws onto one snapshot schema. Divergent schemas are legitimate; only the declaration surface is fixed.
- Making the review gate prove semantic correctness. It proves declared structure, which is what a TBox can carry.
- Any TUI work. `law-simulation-tui` is the consumer and stays blocked.
- Choosing a triple store. The runtime pool's storage is an implementation detail behind the contract.

## Decisions

**1. Invariants are declared as class and property declarations, checked on the TBox.** Each framework invariant is expressible without instances: `ph:Citizen`'s superclass, `ph:Clock`'s superclass and property domains, `ph:CalendarPoint`'s superclass and required properties, `ph:CalendarSpan`'s superclass and temporal relations. The gate asserts these declarations exist and are GFO-grounded, then separately asserts that seeded individuals in `population.ttl` carry label and age. *Alternative considered:* per-instance checks mirroring today's label check. Rejected — that is the exact mechanism that let the drift through.

**2. Framework properties are grounded in GFO, not reused from it.** Each relationship is declared as a `ph:` property, never a reuse of the GFO property directly. Grounding is by `rdfs:subPropertyOf` where the relation coincides with a GFO one — `ph:hasPhase` over `gfo-core:hasSituationPart`, `ph:hasParticipant` over `gfo-core:hasParticipant`, `ph:hasTime` over `gfo-core:hasTime` — and by GFO `rdfs:domain`/`rdfs:range` where GFO has no such relation but the types are knowable. This follows the pattern the predecessor change set for `ph:atDate` and `ph:age`, and it buys two things: a reasoner can check the grounding, and the gate can enumerate the hierarchy by querying one namespace rather than a mixture of GFO and local names. *Alternative considered:* using the GFO properties directly. Rejected — it leaves no hook for the gate and makes "every `ph:` property is grounded" untestable as a single rule.

    The subproperty-only rule was too strong, and working through an `owl:inverseOf` grounding for the calendar-to-phase relation is what exposed it. Two real errors followed. `ph:hasTime` had been subpropertying `gfo-core:timeOf`, which is the *inverse* of `hasTime`, so the ontology asserted the opposite direction from the one its own comment documented. And `ph:marksPhase` genuinely has no GFO counterpart: `owl:inverseOf gfo-core:hasTime` would align perfectly if its object were a Process individual, but it is a Process *class*, because the base calendar is frozen and shared by every repeat and so can only name a phase type — an instance does not exist at review time. Those are two relations over two object types, not one relation. `ph:marksPhase` is therefore grounded by declaring `gfo-light:Chronoid`/`gfo-light:TimeBoundary` as its domain and `gfo-core:Process` as its range, which a reasoner can still use, and asserts nothing false. A property chain over the Chronoid bounds was considered for the same purpose and rejected: `owl:propertyChainAxiom` entails rather than defines, so it would have no effect without a reasoner, and it composes to a Process instance rather than a phase class — the same object-type mismatch. The seeds assert `ph:marksPhase` directly rather than relying on entailment. *Alternative considered:* declare `ph:marksPhase` as the inverse of `hasTime` anyway. Rejected — it would assert that a Process class is the temporal projection of a calendar node, which a reasoner accepts and which is not the meaning. *Alternative considered:* drop the property and bind phases to windows through the manifest instead. Rejected — the calendar would stop saying which phase each window is for, which is what lets a consumer render the plan.

**3. Class-level assertions, not `someValuesFrom` restrictions.** `ph:MayorElectionCycle ph:hasPhase ph:SelfNomination` rather than a subclass restriction. A restriction is more formally correct but expresses only existence, so it cannot say "these are the constituents and no others", which is the thing the TUI needs in order to render a process tree, and it cannot be enumerated reliably. Plain assertions read in a diff, which matters because this artefact is reviewed by a human. *Alternative considered:* an ordered RDF list per process. Rejected — it fixes a phase order in the ontology that the calendar already derives, and would then need a second source to keep in sync.

**4. `ontology.ttl` becomes a frozen TBox; seeds move to a sibling `population.ttl`.** Classes and properties are schema and are what review freezes; individuals are runtime data. Seeds stay reviewable because `population.ttl` is frozen too. At session start the consumer loads seeds into the knowledge graph, so there is exactly one label source and no two-source divergence. The seed stays RDF for a specific reason: once the graph is the snapshot, a non-RDF seed needs a bespoke mapping into triples, and that mapping is per-law code under another name. *Alternatives considered:* (a) keep seeded individuals in `ontology.ttl` — rejected, this yields two label sources (frozen graph plus runtime graph) and a consumer that must try both; (b) a YAML seed — rejected for the mapping reason above; (c) regenerate seeds from `law.txt` at session start — rejected, the reviewed artefact is no longer what runs.

**5. History is the same kind of entity as the present, distinguished by `temporallyFinishedBy`.** A process instance is ongoing exactly when it carries no `temporallyFinishedBy`; a finished one carries it plus an outcome. This replaces `law-framework`'s "the current cycle is the last element", which was an array-ordering convention that happened to work. It also gives past-dependent conditions a uniform address: a law asking about prior instances queries finished individuals of the same class, rather than scanning a bespoke array. A side effect worth naming: this resolves whether snapshots must universally carry election-cycle history — they do not, because a law with no history simply has one ongoing instance, so the requirement becomes about representing prior instances rather than about any particular structure.

**6. Lifecycle bounds take GFO's real shape: `hasTime` to a `Chronoid`.** A process instance relates to a `Chronoid` by `ph:hasTime`, and that `Chronoid` carries `temporallyStartedBy` and `temporallyFinishedBy` pointing at `TimeBoundary` individuals. Attaching a `TimeBoundary` straight to a situation is a widespread shorthand that is not strictly typed, and this framework's whole grounding argument rests on properties a reasoner can follow. Absence of the start bound is what denotes an instance that has not begun, which is how an initialised process — "the next election" — is distinguished from an ongoing one. *Alternative considered:* attaching bounds directly to the process. Rejected as the shorthand above.

**7. Phases and stateful entities are both Processes, and the framework declines to choose.** A time-scoped phase and a per-occurrence entity with its own outcome are both `gfo-core:Process` instances. They differ in cardinality and nesting, not in category, and a law needing a requisition that can be withdrawn or rejected models it as an instance with a `Chronoid` and an outcome. Requiring every law to distinguish them would impose a level count on laws that do not need one, and forbidding it would block laws that do. *Alternative considered:* a framework-mandated distinction between "phase" and "entity" classes. Rejected — GFO gives no basis for it, and the vocabulary is sufficient for both.

**8. The manifest is the single declaration site for act parameters and holder roles; the ontology is a validated reference.** A consumer needs one flat place to learn what to render, so `manifest.yaml` carries `holder_role` and `params[]` with each parameter naming its wire field, its ontology Role, and a `source` from the closed set `selected`/`choices`. Ontology Roles are not a second declaration — the gate asserts each declared Role is one the ontology declares as participating in that ECA's Process class. *Alternatives considered:* (a) verdict carries slots only — rejected, the consumer would have no widget specification before its first check and Lean would be deciding presentation; (b) ontology-only — rejected, the ontology says who is involved but not what to prompt for or from which state; (c) three independent declarations — rejected, that is drift with extra steps. `source` stays a closed vocabulary rather than an expression language, so the consumer's widget set is finite.

**9. Pending duties name their process instance, and acts select their target through parameters.** With two process types unfolding at once, one citizen can hold a duty on each, and a flat `citizen -> [eca]` map cannot say which is which, so a consumer cannot group duties under processes. Each pending entry names the instance. Where a process type has several ongoing instances, the act targets one through a parameter sourced from `choices` over the open instances — so the existing parameter mechanism carries the selection and no new act-envelope concept is introduced. *Alternative considered:* a mandatory process reference on every act. Rejected as redundant where the ECA id is unique to one phase, and it would duplicate information the pending entry already carries.

**10. `apply` receives and returns the whole graph and replaces it wholesale.** Whole-graph rather than delta is chosen knowingly: the framework does not know which triples a given law needs for a given act, so a delta would require declaring the delta's scope, which is the guess decision 9 rejects. The cost is that a one-ballot act rewrites the whole graph, and a long-running law's checks grow monotonically. Accepted deliberately and deferred: the replace-not-merge semantics are fixed now so a delta protocol can be layered on later without changing the contract. *Alternative considered:* changed-triples delta from the outset — rejected as premature, since the round-trip semantics would then be defined in terms of an optimisation whose requirements are not yet known.

**11. The gate verifies what the prompt requests.** The `roleIn` and `playedBy` instruction has been in `onto-v1.md` and ignored in both outputs. Adding it to the prompt again would not help; checking for it will. The prompt therefore stays the source of the *instruction* and the gate becomes the source of the *obligation*, and the structural-diff stability requirement now covers the generated hierarchy so a redraft cannot quietly reshape it. *Alternative considered:* drop the unfulfilled instruction from the prompt and rely on the gate alone. Rejected — the prompt is what tells a generator to produce relationships in the first place, and a law author reading it learns the intended shape.

**12. Relationship work stops at the artefacts.** This change adds declarations, hierarchy, gate checks, and verdict attribution. It does not add runtime machinery, because the predecessor change already made the graph the snapshot: a nomination occurrence becomes a graph individual of its phase's Process class relating to the citizen and the enclosing instance, with no extra encoding. *Alternative considered:* declaring occurrence instances as a distinct concept. Rejected — they are ordinary Process individuals, and a separate concept would be vocabulary for its own sake.

**13. No framework fallback-authority rule.** Decided deliberately rather than deferred: laws may resolve an unheld duty to the oldest citizen, the youngest, or anything else, and the consumer needs no framework support either way because it reads holders from `pending` instead of computing them. Making oldest a framework guarantee would have been convenient but would bake one governance idiom into the framework, and any law wanting a different rule would have to route around it.

**14. Causality is allowed where it is structural and forbidden where it would be evaluated.** This decision was originally the opposite — a blanket prohibition on `leadsTo`, `causes`, `resultsFrom`, and `causedBy` in the artefacts — on the reasoning that sequencing belongs to the calendar and causation is rule truth. A counterexample dissolved half of that: a law under which a candidate who withdraws during polls halts the election and postpones it. Nothing about that dependency is a fact about dates, so no calendar bound can express it, and Lean already computes that election's repeat dates, so the machinery to materialise a new calendar span is being added by the predecessor change regardless. Ordering and causation turned out to be separable after all, and the fence is drawn between them by asking what the relation's subjects are.

| Relation connects | Allowed | Reasoning |
|---|---|---|
| phase → phase, as ordering | nowhere | Phases overlap; the nomination window covers days 0 through 10 while announce is day 0 and prepare is day 9, so a linear chain would assert something false. Calendar `Chronoid` bounds give order and overlap from one source, so an ordering relation would also state the same fact twice. |
| Process `ph:causedBy` State | ontology, as a subproperty of `gfo-core:causedBy` | It is readable structure: the ontology says a withdrawal *can* stop an election, which a guide can display before any check runs. |
| condition → guard | Lean only | Whether the State actually holds, and so whether the change fires now, is an evaluation. `prompts/manifest-v1.md` already states that "conditions, holders, winners live in Lean". |

The line is structural versus evaluated, and neither side duplicates the other: the ontology states what *may* happen, the graph and verdict record what *did*. The predecessor's graph-as-snapshot work also forced the distinction into the open — its whole point was that the graph holds instance state, so a proposition about a State holding belongs in the graph while the proposition that it *can* affect a Process belongs in the schema.

*Alternative considered:* leave the blanket prohibition and let the revocation case live entirely in Lean. Rejected — then the ontology would not say the dependency exists at all, a guide could not show a citizen that withdrawing would halt the election, and the law's structure would be invisible outside its guard. *Alternative considered:* general `leadsTo` between any situations. Rejected — it reintroduces exactly the ordering-between-phases problem, and `causedBy` from a State carries the revocation case without it.

**15. Erasure is prohibited outright, and the prohibition is checked mechanically.** No ECA removes an individual from the graph. What a later rule may affect is only how an individual is counted. This was initially scoped to "contributions a finished process accumulated", on the assumption a law might want a retracted fact to leave no trace; that scope was wrong. A vote cast is a fact about the past and no rule has the power to unmake it — the only available lever is whether it counts, so a cancelled election records that its ballots do not count while the ballots remain. Erasure is not something a law lacks by policy, so a policy statement is the wrong instrument: it is asserted instead as a property, with the gate applying each ECA in turn and confirming every prior subject survives. Verified against both shipped oracles, where no accepted act removes a subject across announce, nominate, prepare, vote, count, and proclaim, so this records behaviour the artefacts already have rather than constraining them newly. Deliberately stated as subject monotonicity, which is the axis the rule is about; whether a property *value* could be overwritten is a weaker and separate guarantee, and is not claimed here.

**16. Clock field names are framework-fixed, not declared per law.** `ph:dayIndex` and `ph:atHour` are fixed exactly as `ph:age` is fixed on `ph:Citizen`; fixing one field of a class while declaring another would be worse than either. No law currently uses different names, so a declared variant would have no case to exercise it and only validation surface to maintain. *Alternative considered:* `manifest.clock: {day_field, hour_field}`. Rejected on symmetry and dead validation.

**17. `ph:Clock` is a `gfo-light:TimeBoundary` sharing `ph:dayIndex` with `ph:CalendarPoint`.** One property on both classes means "which calendar point is current" is a single ordered comparison against the clock for any law. Keeping them separate classes would need two comparison paths and defeat the point of declaring them at all.

**18. The driver writes `ph:Clock` directly; there is no clock-advancement verb.** Advancing time is a simulation control, not a rule, so it does not belong behind a rule-enforcing boundary. The practical argument is decisive: the oracle is a ~122 MB cold-spawned binary, and clock advance is the most frequent interaction in the whole consumer, so a round trip per tick would be felt on every step. The resulting boundary is one line: *the driver writes the clock; every other change goes through `apply`.* *Alternatives considered:* (a) an `oracle tick` verb — rejected on latency, and it would put rule-adjacent writes behind a boundary that exists to prevent exactly the kind of unreviewed mutation a tick is; (b) Python owning the clock as today — rejected, it is equivalent to the chosen option but without the contract making it explicit.

**19. Untrusted clock input becomes a totality obligation on Lean.** Once the driver writes the clock, `day` and `hour` are arbitrary and `check`/`apply` must be total over them. Both compiled oracles were verified total today across `day` in {0, 9999, 100000} and `hour` in {0, 47, 999}. That is a property to lock down rather than an accident: `electionDayK k = base + gap * k` is safe under any input, while any future *subtraction* on `Nat` (a deadline as `day - announceDay`) would underflow on exactly these inputs. Hence a clock-totality check in the gate, run against the compiled oracle.

**20. `readings` replaces the election-specific result field.** `wouldWin` exists only because mayor was built first; a law with a different result type would need a verdict shape change. `readings` entries carry a law-chosen id, a kind from the closed set `decimal`/`ref`/`flag`, and a value, with `ref` naming the ontology class so labels resolve. `phase` stays top-level because both specs treat it as a first-class reading. Every kind is one rendering case in the consumer, which is why the set is kept closed — a kind is only added when a law genuinely cannot be expressed without it.

**21. The knowledge graph is the snapshot; `check` and `apply` exchange typed instance triples.** The decisive argument is that the framework cannot know in advance what a law needs to decide, so any projection is a guess frozen into the contract. Sending the whole graph and letting each law's FOL conditions select what matters keeps that judgement where it belongs. This is also more faithful to the spec than a projection would be — `law-framework` already says the snapshot "enumerates the full finite population" under a closed world, which describes whole-graph, not a slice. Three things collapse as a result: the seam between the oracle's JSON state and the consumer's display graph disappears; ordering stops being an array convention and becomes a declared property; and history stops being a per-law special field. *Alternatives considered:* (a) keep a bespoke JSON state and add a projection — rejected, it fixes a guess into the contract and keeps both representations; (b) declare a projection per law — rejected for the same reason, at more cost.

**22. The consumer validates every returned subject is typed by a declared class.** Because `apply` replaces rather than merges, a malformed response is data loss rather than a partial write. Making an untyped subject an error, checked before commit, keeps the graph from silently diverging from the oracle's state. *Alternative considered:* accept untyped subjects and resolve types later — rejected, it reintroduces exactly the two-representation problem decision 9 removes.

**23. The oracle is total over triples it does not need.** Direct consequence of decision 9: conditions select from the graph rather than being pre-filtered, so Lean must tolerate irrelevant individuals and must not fail on them. This is what makes whole-graph safe rather than merely wasteful.

**24. Violation witnesses become structured, and `detail` stays.** The FOL subset is universals and existentials over finite sets plus counting, so a failed witness is either the individuals that break the quantifier or the counts that fell short — `refs` and `counts` cover it without per-law fields. This also converges with `artefacts/README.md`, which has always documented a nested witness object; the compiled oracle flattened it, so the docs were right and the code diverged. `detail` is retained because a violation describes an arbitrary failed condition that no finite manifest can enumerate, and `law-framework` already made this call for `apply` rejections, which "double as the guide's messages". Dropping `detail` would make violations less displayable, not more. The achievable requirement is the weaker one actually specified: no verdict field is named for a process concept, and `detail` is not. *Alternative considered:* templating violations in the manifest with a generic fallback — rejected as untestable in the general case.

## Risks / Trade-offs
- **[Risk] Three surfaces can drift** — manifest declarations against the ontology's Process and Role classes, and both against `oracle list` and Lean's `Act` parameters. → Mitigation: the gate cross-validates all three and names the mismatch; drift becomes unfreezable rather than latent.
- **[Risk] Making the graph the snapshot means Lean must reconstruct typed state from an unordered multiset of triples.** This is the largest single piece of work in the change and touches both rule sets. → Mitigation: ordering becomes explicit declared properties, which removes the one thing that genuinely required order; the remaining reconstruction is a single fold, and the existing suites verify it.
- **[Risk] Whole-graph round-trip makes every check grow with the graph, so long-running laws degrade monotonically.** Deliberately deferred per decision 11. → Mitigation: the replace-not-merge semantics are fixed now, so a delta protocol can be layered on without a contract change; the review gate gains a round-trip check that would surface a latency problem as a correctness one first.
- **[Risk] TBox-only is a breaking departure for anything reading individuals from `ontology.ttl`.** Existing tooling in this repo assumes otherwise, including the ontology checks themselves. → Mitigation: those checks move to `population.ttl` and the runtime graph in the same change, so no consumer is left reading a file that no longer holds individuals.
- **[Risk] The clock-totality check is new infrastructure with no precedent here, and a law that later needs calendar subtraction will break it.** → Mitigation: the check runs against the compiled oracle so it fails loudly at gate time rather than at play time; treat a totality failure as blocking.
- **[Trade-off] The gate gets stricter, so existing drafts stop passing.** Both shipped sets must be migrated and re-frozen; that was already required by the ontology split.
- **[Trade-off] Consumers now own a graph write path.** Accepted: the consumer already writes the clock, and replacing a graph wholesale is simpler to reason about than merging one.
- **[Risk] Making relationship checks mandatory rejects the shipped sets immediately.** They must be redrafted and re-frozen. → Mitigation: bounded work — relationship declarations add no Process class and properties carry no mirror-by-name Lean counterpart, so `rules.lean` is untouched.
- **[Risk] Relationship checks invite ambiguity about whether a relation is structural or an evaluated restatement.** → Mitigation: the gate rejects a `ph:causedBy` whose endpoints are not a State and a Process, and no artefact asserts that a dependency has fired.
- **[Risk] The narrowed fence could be read as "the law text's ordering is unrepresented".** It is represented, in the calendar and in Lean, just not twice. → Mitigation: the gate diagnostic names the destination for each rejected relation.

## Migration Plan

Artefact-contract change, not a deployment. Order: prompts to v2 → both ontologies reduced to TBoxes and `population.ttl` seeds written → both rule sets reworked to derive state from triples → gate checks → rebuild oracles → re-freeze both sets → script updates.

Rollback is artefact-level: the previous frozen sets and their binaries keep working together, and nothing outside `artefacts/` and `scripts/` depends on the new contract. `law-simulation-tui` remains blocked until this lands, and must be corrected to build on the resulting contract rather than implemented as written.

## Open Questions
- Whether `ph:age` is a plain data property or a reified `gfo-light:Quality` instance. The requirement says only that a `ph:age` value is present; reification is worth it if age history must be preserved, which the tie-break may warrant. Affects ontology authoring only, not the contract.
- Where the runtime graph is held — an in-memory triple graph or a plain indexed structure, and whether SPARQL is wanted as a query surface for the guide. No contract impact; the uniform IRI-to-label lookup and typed-subject validation are what must survive either choice.
- The step at which a graph is large enough for whole-graph round-trip to be felt, and what the retention story is for laws with unbounded history. The spec does not depend on the answer; only performance and authoring guidance do.
- Whether `roleIn` and `playedBy` should be framework subproperties with their own `ph:` names, or the plain GFO properties, given the prompt already names the GFO forms and no grounding failure has been observed for them. The grounding rule as specified requires every `ph:` property to be grounded, which the plain GFO names satisfy trivially by not being `ph:` properties — a gap in the rule rather than a design question, and cheaper to resolve by naming them `ph:roleIn` and `ph:playedBy`.
- Whether a law whose text names no stages at all should be permitted to declare a Process with no phases. A process with no decomposition is expressible and the orphan check does not catch it, since the root is a legitimate root. Affects one gate edge case only.
- Whether a `ph:causedBy` from a State to a Process should also permit a State to cause another State, which would express a transition between situations directly rather than through a Process. Not needed by any case considered so far, and permitting it would blur the Process/State distinction the vocabulary relies on.
